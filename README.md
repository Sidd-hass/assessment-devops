# DevOps Assessment: Terraform + Database Reliability

AWS infrastructure design in Terraform (plan-only, no deployment needed) plus a local PostgreSQL
database with migrations, seed data, an optimized query, and backup/restore scripts.

```
.
├── docker-compose.yml            # local PostgreSQL 16
├── .env.example                  # optional overrides (copy to .env)
├── db/
│   ├── migrations/               # 001 tables, 002 indexes
│   └── seed/                     # seed.sql (300 bookings), seed_large.sql (optional, 200k rows)
├── scripts/                      # backup.sh, restore.sh, verify_restore.sh, seed.sh, explain.sh
├── infra/
│   ├── modules/{network,ecs,rds}
│   └── envs/{dev,prod}           # each: main/variables/providers/backend/outputs + terraform.tfvars
└── .github/workflows/terraform-plan.yml
```

Requirements: Docker with Compose v2 for the database tasks; Terraform >= 1.5 for the infra tasks.

## Part 1 & 2: Terraform

### Architecture

```
Internet ──► ALB (public subnets) ──► ECS Fargate tasks (private subnets) ──► RDS PostgreSQL (private subnets)
              alb-sg: 80/443 from       ecs-sg: app port from alb-sg only       rds-sg: 5432 from ecs-sg only
              the internet
```

Key decisions:

- **Network module**: VPC, 2 public + 2 private subnets across 2 AZs, IGW, NAT gateway(s), route tables,
  and all three security groups. The SGs live here (not in the ECS/RDS modules) so the RDS SG can reference
  the ECS SG without a circular module dependency. Rules reference security groups instead of CIDRs.
- **RDS is private**: `publicly_accessible = false`, private subnets only, and the RDS security group has a
  single ingress rule (5432 from the ECS SG) and no egress rules. Storage is encrypted, logs go to
  CloudWatch, and the master password is generated by RDS into Secrets Manager
  (`manage_master_user_password`), so no password exists in code or tfvars. The ECS task receives it as a
  container secret.
- **ECS module**: cluster, task definition (nginx placeholder), Fargate service in private subnets with no
  public IP, ALB + target group + listeners, CloudWatch log group, separate execution and task IAM roles,
  and a deployment circuit breaker with rollback. If `certificate_arn` is set, the ALB serves HTTPS and
  redirects HTTP to it.

### Environments

| Setting | dev | prod |
|---|---|---|
| NAT gateways | 1 (shared) | 1 per AZ |
| Fargate task | 0.25 vCPU / 512 MiB x 1 | 1 vCPU / 2 GiB x 3 |
| RDS instance | `db.t4g.micro`, 20 GiB (max 50) | `db.m6g.large`, 100 GiB (max 500) |
| RDS Multi-AZ | false | true |
| Backup retention | 3 days | 14 days |
| RDS deletion protection | **false** | **true** (plus final snapshot on delete) |
| ALB deletion protection | false | true |
| Log retention | 7 days | 90 days |
| State backend | `hotel-tfstate-dev` / `hotel-tf-locks-dev` | `hotel-tfstate-prod` / `hotel-tf-locks-prod` |

Each environment has its own `variables.tf`, `terraform.tfvars`, `backend.tf` (S3 state + DynamoDB lock),
and `providers.tf`.

### Review commands (no AWS account needed)

```bash
cd infra
terraform fmt -check -recursive

cd envs/dev          # repeat for envs/prod
# plan-only: swap the S3 backend for a local one (file is git-ignored)
printf 'terraform {\n  backend "local" {}\n}\n' > backend_override.tf
terraform init
terraform validate
AWS_ACCESS_KEY_ID=dummy AWS_SECRET_ACCESS_KEY=dummy terraform plan -refresh=false
```

Notes:

- Each env's `backend.tf` points at a real S3 bucket + DynamoDB lock table, so a plain `terraform init`
  needs valid AWS credentials and the bucket to exist. `backend_override.tf` is a standard Terraform
  override file that replaces it with a local backend for review. (`init -backend=false` is not enough:
  `plan` then fails with "Backend initialization required".) For a real deployment, create the
  bucket/table once, delete `backend_override.tf`, and run `terraform init` with real credentials.
- `providers.tf` sets `skip_credentials_validation`, `skip_requesting_account_id` and
  `skip_metadata_api_check`, and the code uses no live-lookup data sources, so
  `plan -refresh=false` works offline with dummy credentials. Remove those flags for real deployments.
- A plan with no state shows every resource as a create, which is what we want for review.

## Part 3: GitHub Actions (optional part, included)

`.github/workflows/terraform-plan.yml` runs on pull requests touching `infra/**`, once per environment
(matrix: dev, prod):
`fmt -check` -> local backend override -> `init` -> `validate` -> `plan -refresh=false`.
The plan is published three ways: visible in the job log, uploaded as the `tfplan-<env>` artifact, and
posted/updated as a PR comment (one sticky comment per environment).

## Part 4–6: Local database

### Start it

```bash
cp .env.example .env        # optional, defaults already match
docker compose up -d        # add --wait to block until healthy
docker compose ps           # STATUS should be "healthy"
```

On the first start of an empty volume Postgres runs, in order, `001_create_tables.sql`, `002_indexes.sql`,
and `seed.sql` (via `/docker-entrypoint-initdb.d`). To start from scratch: `docker compose down -v`.

Verify:

```bash
docker compose exec db psql -U app -d hotel -c "\dt"
docker compose exec db psql -U app -d hotel -c \
  "SELECT city, COUNT(*) FROM hotel_bookings GROUP BY city ORDER BY 2 DESC;"
docker compose exec db psql -U app -d hotel -c \
  "SELECT COUNT(*) AS bookings, (SELECT COUNT(*) FROM booking_events) AS events,
          COUNT(DISTINCT org_id) AS orgs, COUNT(DISTINCT status) AS statuses FROM hotel_bookings;"
```

Expected: 300 bookings, 5 organizations, 4 statuses, 6 cities (delhi weighted highest, about a third),
and roughly 400 events covering about 87% of bookings.
Re-seed any time with `./scripts/seed.sh` (it truncates first).

### Index choice

Query:

```sql
SELECT org_id, status, COUNT(*), SUM(amount)
FROM hotel_bookings
WHERE city = 'delhi' AND created_at >= NOW() - INTERVAL '30 days'
GROUP BY org_id, status;
```

Index (`db/migrations/002_indexes.sql`):

```sql
CREATE INDEX idx_hotel_bookings_city_created_at_cov
    ON hotel_bookings (city, created_at) INCLUDE (org_id, status, amount);
```

Why:

1. **`city` first**: it is an equality filter, so it narrows the b-tree to one contiguous city section.
2. **`created_at` second**: the range filter then becomes one contiguous slice inside that section, so only
   the last 30 days of delhi bookings are read. The reverse order (`created_at, city`) would scan every
   city for the date range and filter afterwards.
3. **`INCLUDE (org_id, status, amount)`**: these are the only other columns the query reads (grouping and
   aggregation). Storing them in the index leaf pages allows an **Index Only Scan**, with no heap lookups.
   They are in `INCLUDE`, not in the key, because they are never searched on and this keeps the key
   small. `INCLUDE` needs PostgreSQL 11+.

Secondary index: `booking_events (booking_id, created_at)` supports loading one booking's event timeline
and the foreign-key check.

Trade-off: a covering index is larger and adds write cost per insert. That is acceptable for a read-heavy
reporting query.

### Seeing the index work

`./scripts/explain.sh` already shows an Index Only Scan on the 300-row seed, but at that size the planner
could just as well pick a sequential scan (the whole table fits in a few pages). To see the index matter,
add volume and look at the plan:

```bash
docker compose exec -T db psql -U app -d hotel < db/seed/seed_large.sql   # +200k rows, runs VACUUM ANALYZE
./scripts/explain.sh
```

Expect `Index Only Scan using idx_hotel_bookings_city_created_at_cov` with a low `Heap Fetches` count
(the `VACUUM` in the script keeps the visibility map fresh, which index-only scans need).
To compare, `DROP INDEX idx_hotel_bookings_city_created_at_cov;` and re-run: it becomes a sequential scan.
Run `./scripts/seed.sh` afterwards to go back to the small dataset.

## Part 6: Backup and restore

```bash
./scripts/backup.sh                 # -> backups/hotel_<UTC timestamp>.dump
./scripts/restore.sh                # restores the newest dump into a fresh DB "hotel_restore"
./scripts/restore.sh backups/hotel_20260101T120000Z.dump   # or a specific file
```

- `backup.sh` runs `pg_dump --format=custom` inside the container, writes to a `.partial` file, checks the
  archive is readable with `pg_restore --list`, then renames it, so a failed backup never leaves a
  half-written `.dump`. The file name contains the UTC timestamp.
- `restore.sh` drops and recreates the separate `hotel_restore` database (never the source DB) and runs
  `pg_restore --exit-on-error` into it, then prints row counts.

### Verify that the restore worked

Automated check, which compares both databases:

```bash
./scripts/verify_restore.sh
# source  (hotel):         300|<events>|<sum>|<md5>|<md5>|<indexes>
# restore (hotel_restore): 300|<events>|<sum>|<md5>|<md5>|<indexes>
# PASS: restored database matches the source.
```

It compares row counts of both tables, `SUM(amount)`, an md5 checksum of every row of both tables, and
the number of indexes (so the index was restored too).

Manual check:

```bash
docker compose exec db psql -U app -d hotel_restore -c "\dt"
docker compose exec db psql -U app -d hotel_restore -c "\di"
docker compose exec db psql -U app -d hotel_restore -c \
  "SELECT org_id, status, COUNT(*), SUM(amount) FROM hotel_bookings
   WHERE city='delhi' AND created_at >= NOW() - INTERVAL '30 days' GROUP BY org_id, status;"
```

To prove the restore does real work, damage the source and restore into a fresh DB:

```bash
./scripts/backup.sh
docker compose exec db psql -U app -d hotel -c "DELETE FROM booking_events;"   # simulate data loss
./scripts/restore.sh                                                           # hotel_restore still has the events
docker compose exec db psql -U app -d hotel_restore -c "SELECT COUNT(*) FROM booking_events;"
```

### Cleanup

```bash
docker compose down -v      # stops the DB and deletes the data volume
```
